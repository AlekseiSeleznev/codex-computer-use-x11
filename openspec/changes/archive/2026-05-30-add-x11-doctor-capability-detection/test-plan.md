## TDD Strategy

Use the project-local `tdd` skill with vertical RED -> GREEN -> REFACTOR slices. Each slice starts from one observable behavior through either the public CLI (`codex-computer-use-x11 doctor --json`) or the public crate API (`codex_computer_use_x11::doctor`) using a fakeable `ProbeContext`/boundary seam. Do not write production probe logic before the slice has RED evidence.

Test priority:

1. Preserve the existing bootstrap JSON contract before adding new facts.
2. Add one capability/probe family at a time with fake env/command/socket/fixture boundaries.
3. Aggregate readiness only after the individual facts exist.
4. Keep CLI exit behavior and non-invasive/no-secret behavior observable through public commands.
5. Treat live Cinnamon/X11 smoke as final verification evidence only after unit/fixture tests are GREEN.

No horizontal "all tests first, all implementation later" work is allowed. The tasks artifact must order each production change with its corresponding RED/GREEN evidence.

Carry-forward items that this test plan explicitly covers:

- `checks[]` entries must be enumerated and the stale bootstrap `no-live-x11-probes` check must be retired or replaced with a truthful non-invasive/read-only probe-policy check.
- `can_query_windows` uses one canonical fixture-backed EWMH/root probe: `xprop -root _NET_SUPPORTING_WM_CHECK _NET_ACTIVE_WINDOW`. The success fixture should use a parseable `_NET_SUPPORTING_WM_CHECK` X11 id and requested property output; do not over-constrain by requiring live `wmctrl -m` or by rejecting a valid `_NET_ACTIVE_WINDOW` no-active-window value when the supporting-WM property is valid.
- `source_overlay` is static acceptance metadata. Runtime facts live in `portals`, `screenshots`, and `input`.
- Standalone `abs_pointer` is derived locally from `/dev/uinput` read/write facts; it must not call or embed the target repo `CapabilityMap`.
- `portals.screencast` and `portals.input_capture` are additive report-only target-vocabulary facts in this change unless a later spec expands them into readiness gates.
- `capabilities.planned` remains explicit. `x11-ewmh-windowing` must stay planned until a later listing/focus change implements it or moves it into a named capability fact; it must not be silently emptied.
- If downstream automation begins to depend on the expanded readiness vocabulary as a guaranteed cross-consumer contract beyond additive `doctor --json` behavior, use the ADR reopen trigger recorded in `adr.md`.

Contract clarifications for downstream tasks:

- Slice 1 is intentionally a single contract-preservation integration/regression test for additive JSON compatibility. Do not split it into isolated field-level unit tests that would lose the guarantee that all existing bootstrap fields survive together while new facts are added.
- The suggested `checks[]` names in Slice 2 are draft implementation anchors, not a cross-consumer compatibility contract. The binding requirements are the spec-required `name`/`ok`/`detail` shape, truthful capability-stage checks, and removal of stale bootstrap `no-live-x11-probes` text. Tasks may choose equivalent check names without another artifact update cycle when the chosen names cover the same categories; `tasks.md` must explicitly record the final chosen check names in its evidence notes before Slice 2 is marked complete so archive review has a concrete anchor.
- Slice 9 intentionally makes an internal report-construction/serialization failure seam a normative test requirement for this change so CLI failure behavior can be proven without partial JSON. No TDD exception is pre-approved; if the seam proves impractical, stop and seek an explicit test-plan exception update before weakening the test.
- `readiness.can_focus_apps` and `readiness.can_focus_windows` remain `false` for this whole change and until a later accepted design/spec implements verified focus behavior. The false values are not merely transient within the current implementation stage.
- For readiness priority fixtures, the AT-SPI blocker condition is `can_build_accessibility_tree == false` because the AT-SPI bus is unreachable or tree extraction is unavailable. A reachable AT-SPI bus with unavailable tree extraction still yields `can_build_accessibility_tree == false` and a blocker entry; the two AT-SPI fixtures are differentiated blocker evidence, not a blocker/degraded pair. Optional accessibility/toolkit facts that do not prevent tree readiness may be reported as `degraded_reasons`, but they must not outrank a real blocker.
- Preferred pgrep/process-hint path for this change: do not add a separate ydotoold process-hint field; socket connectability is the authoritative ydotool readiness signal. Therefore `pgrep` is absent from Slice 4 and Slice 5 by default. If tasks deliberately add a process-hint field anyway, Slice 5 must add the named `pgrep` fixture test and evidence before completion.
- Slice 8 may implement the recommendation-priority fixtures as parameterized/table-driven tests. This does not require another artifact update cycle as long as each priority tier has a clearly labeled case and the evidence log records RED/GREEN evidence per tier.
- The two AT-SPI blocker fixtures in Slice 8 must produce textually distinct blocker messages (for example, `AT-SPI bus unreachable` vs. `AT-SPI bus reachable but tree extraction unavailable`) so evidence can prove both states were tested without relying on implementation internals. `tasks.md` must record the final chosen blocker strings before Slice 8 is marked complete.
- `tasks.md` must plan the thin CLI handler/report-builder/`Write` seam for Slice 9 before implementation of that slice begins. If tasks cannot place the seam without production-only complexity, stop for an explicit test-plan exception update instead of weakening the failure-path test during apply.

## Mocking / Boundary Policy

- Mock only system boundaries: environment variables, PATH/command execution, DBus command output, filesystem access checks, Unix socket connect attempts, and target-checkout path observation.
- Do not mock internal collaborators that we control. Readiness aggregation should consume real report facts built by earlier slices.
- Use fake command output or fixture files for `busctl`, `gdbus`, `xprop`, `wmctrl`, `command -v`, and failure cases. Use `pgrep` fakes only if tasks opt into a process-hint field per Slice 5. Tests must not require live X11, live portals, live AT-SPI, live ydotoold, or current `/dev/uinput` permissions.
- Use temporary directories/files/sockets for filesystem and socket tests. Do not write to the real local integration target checkout.
- Do not read `.secrets.local.env`; no test should require real credentials or private URLs.
- Keep `source_overlay` tests on stable metadata fields (`target_checkout_modified`, `strict_portal_required`, `target_vocabulary`, `screenshot_provider_mapping`) rather than prose-only `notes`.
- Treat `CODEX_DESKTOP_LINUX_FULL_PATH` and the documented local default path as non-secret path configuration only; do not assert or print private data from target files.
