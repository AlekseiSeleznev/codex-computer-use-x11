## TDD Strategy

Use the project-local `tdd` discipline with vertical, public-boundary slices. Do not batch all tests before all implementation. Each behavior starts with one failing check against either the target patcher public test boundary (`node --test scripts/patch-linux-window-ui.test.js`) or this repository's overlay-manager test boundary (`cargo test --test source_overlay_scripts ...`). Production changes are then limited to the minimum needed for that slice to pass, followed by GREEN evidence and refactor while green.

The target repo `/home/as/Документы/AI_PROJECTS/codex-desktop-linux-full` owns Computer Use settings webview patch behavior. This repo `/home/as/ai-projects/codex-computer-use-x11` owns the installer/overlay manager and OpenSpec evidence. Live `/opt` asset checks are smoke evidence after fixture tests, not the first RED boundary.

## Mocking / Boundary Policy

- Target settings behavior uses minified webview fixture strings and exported target patcher/resolver functions as the public boundary.
- Runtime payloads are plain fixture objects containing plugin ids, marketplace names, availability booleans, and row-shape facts. Do not mock internal helper calls when the resolver can be exercised directly.
- Current-repo installer tests use temporary fake target checkouts and temporary fake live asset directories. They may simulate root-owned live paths with normal temp files; no real `/opt` writes are allowed in automated tests.
- Live Codex Desktop verification is a smoke boundary only after fixture tests. If the running Electron process caches stale assets, record the restart blocker and use extracted/live asset report evidence.
- Do not read `.secrets.local.env`; no external systems or credentials are required.
